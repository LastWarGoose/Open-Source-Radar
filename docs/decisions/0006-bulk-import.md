# Массовое наполнение и первые замеры

17 ноября 2026. Решения зафиксированы до большого запуска. Этап 5 завершён;
результаты импорта и нагрузочные показатели сохранены в [отчёте](../evidence/stage5-2026-11-17.md).

## Выборка

Один снимок официального JSON Index API `https://pypi.org/simple/`.
Сохраняются serial, ETag, SHA-256 исходного JSON и сжатый оригинал в `.runtime/stage5/`.
Манифест с 15 000 кандидатами находится в `docs/evidence/stage5/selection.json`.
Имена нормализуются по Python packaging и дедуплицируются. Порядок задаётся
SHA-256 от `open-source-radar-stage5-v1`, NUL и нормализованного имени.

Цель — 10 000 успешно импортированных различных имён. При окончательной ошибке
кандидата берётся следующий из сохранённого списка. Общий предел — 15 000 кандидатов.
Это выборка имён реестра, не рейтинг популярности. В неё могут попадать учебные,
малые и заброшенные проекты. Отбор успешных стабильных релизов дополнительно
смещает результат к доступным проектам с валидными метаданными. Ошибки раскрываются.

Для каждого кандидата JSON API сообщает метаданные проекта и доступные релизы.
Выбирается максимальная PEP 440 версия без prerelease/dev, имеющая хотя бы один
неотозванный файл. Метаданные и requirements выбранной версии читаются отдельно,
если она отличается от версии в корневом JSON. Отсутствие стабильного релиза,
невалидная версия/requirement и слишком большой ответ фиксируются как ошибка.
Код пакетов и архивы не скачиваются и не выполняются.

Сохраняется подробная запись выбранной версии. Полная история версий не импортируется;
UI продолжает явно показывать только загруженные версии. Старые реальные данные
и помеченные синтетические записи предыдущих этапов сохраняются.

## Квоты и обогащение

Профиль `compose.bulk.yaml` задаётся явно при запуске:

| Источник | Запросов/час максимум | Минимальный интервал | Параллельных consumers |
|---|---:|---:|---:|
| PyPI | 6000 | 0,5 с | 1 |
| OSV | 6000 | 0,5 с | 1 |
| GitHub | 30 | 1 с | 1 |

PyPI рекомендует распределять большие загрузки во времени. Даже без сетевых
задержек 10 000 запросов при этих настройках требуют около 1,5 часа; дополнительные
запросы версий, ошибки и обработка увеличивают время. Профиль не отменяет Retry-After,
backoff, лимиты ответа, таймауты и общий бюджет попыток. Увеличение числа workers
не увеличивает квоту: её состояние и блокировка находятся в PostgreSQL.

OSV проверяет выбранную версию каждого успешно импортированного пакета. Ошибка
не считается пустым успешным ответом. У GitHub нет настроенного токена; официальный
неаутентифицированный лимит — 60 запросов/час, локально используется половина.
Для этого запуска GitHub проверяется только для кандидатов с позициями
0,500,…9500, максимум один объявленный репозиторий на пакет (первый в нормализованном
лексикографическом порядке). Это максимум 20 sampled пакетов, не весь каталог.
Пакеты без проверки остаются UNKNOWN, не получают фиктивные stars или связи.
Охват GitHub раскрывается в отчёте, общая сортировка ставит неизвестные stars в конец.

## Возобновление

Защищённая mutation `requestCampaign(requestKey, names, target)` сразу возвращает
ID, статус и счётчики. Манифест хранится в существующем `import_jobs.checkpoint`;
`source_work` является долговечным журналом позиции и результатов. Поддерживаются
до 15 000 кандидатов, цель до 10 000. В очереди одновременно не более 40
незавершённых пакетов, без переполнения цели успешными результатами.

Повтор requestKey с тем же манифестом идемпотентен, другой манифест отклоняется.
Beat и завершение worker продвигают кампанию под блокировкой её строки. Большой
манифест не переписывается на каждый пакет. Перезапуск Python-наблюдателя или
контейнера не теряет позицию. Исчерпание кандидатов означает failed, не успех.
Успех кампании означает сохранение PyPI и постановку OSV, не завершение обогащения.

## План измерений

Пороги остаются из TEST_PLAN: p95 каталога ≤500 мс, карточки/поиска ≤1000 мс,
неожиданные транспортные или GraphQL-ошибки <1%. HTTP 200 с errors — ошибка.
Основной профиль: 20 VU, 1 с пауза, 2 минуты прогрева и 10 минут измерения.
Смесь: 60% каталог, 25% карточка, 10% поиск, 5% чтение личных подборок.
До аккаунтов этапа 6 используются две изолированные dev-идентичности только
для чтения; 20 разных учётных записей этот прогон не имитирует.

Стресс: 20/50/100 VU по 3 минуты, остановка при ошибках >10% после начального
периода. Первые замеры выполняются до стресса. Отдельно проверяются планы SQL,
индексы и число запросов для 20/100 родителей на реальном наборе.
Кеш: request-scoped DataLoader, PostgreSQL buffers; глобального кеша публичных
ответов в Redis пока нет. Холодный замер после перезапуска API означает холодные
кеши приложения, не очищенные дисковые/OS buffers. Это различие раскрывается.
Отказ Redis проверяется отдельно, без заявления об измерении несуществующего кеша.

Нагрузочный генератор k6 1.0.0 в отдельном локальном контейнере; ресурсы Docker
общие с приложением. Во время основной нагрузки Beat и source consumers остановлены:
внешние источники не участвуют. Отдельный короткий замер во время импорта измеряет
конкуренцию за ресурсы. Сеть нагрузочного контейнера ограничена локальным gateway.

## Команды воспроизведения

Детерминированные проверки кампании не обращаются к внешним API:

```sh
docker compose build checks
uv run python -m scripts.verify_campaign
```

Проверяются предел очереди, восстановление, замена отклонённых кандидатов,
идемпотентность, запрет обычного resume для кампании и точное достижение цели.
Проверка возвращает ранее запущенные consumers с прежними квотами.

При первом запуске на новом окружении создать снимок один раз:

```sh
uv run python -m scripts.select_stage5
```

Если `docs/evidence/stage5/selection.json` уже существует, использовать его.
Скрипт специально отказывается перезаписывать выборку.

```sh
docker compose -f compose.yaml -f compose.bulk.yaml up -d --wait catalog-importer security-importer repositories-importer beat
uv run python -m scripts.run_stage5
```

Если нужен локальный `compose.override.yaml`, добавить `-f compose.override.yaml`
между основным файлом и bulk-профилем. На текущем хосте он сохраняет рабочее
DNS-сопоставление OSV с проверкой TLS для официального имени; ограничение обычного
сетевого маршрута не считается исправленным. Пароли и токены передаются из `.env`.

Повторный запуск `run_stage5` продолжает ту же кампанию. Внутри неё максимум 40
ожидающих заданий; обычная `resumeImport` кампании не поддерживает — повторяется
`requestCampaign` с исходным манифестом. Время завершения сохраняется при повторе.

После окончания PyPI и обогащения выполнить:

```sh
uv run python -m scripts.measure_stage5 <campaign-id>
```

Скрипт требует 10 000 успешных пакетов и отсутствие ожидающих заданий обогащения.
Он сохраняет отчёт по источникам, выбранные версии, SQL-планы и среду; останавливает
сборщики, перезапускает API, измеряет холодный старт, прогрев, baseline и stress,
проверяет чтение при остановленном Redis и восстанавливает сервисы с обычными квотами.
Повторные замеры требуют отдельного `--run-name`: предыдущие результаты не стираются.
Возврат ненулевого кода означает ошибку либо нарушение порога; отчёт нужно проверить.

Для отдельного короткого теста при работающих сборщиках:

```sh
uv run python -m scripts.load_stage5 contention --output docs/evidence/stage5/load-contention
```

Для сопоставимого теста на полном наборе после baseline:

```sh
uv run python -m scripts.contention_stage5 <campaign-id>
```

Он обновляет метаданные 100 уже загруженных пакетов, выбранных по сохранённым
записям без project URLs, и выполняет минутный прогон с той же полной когортой.
Сохраняются состояния до/после, подтверждающие реальное перекрытие загрузки и чтения.
Сборщики используют прежние bulk-квоты; генератор не обращается к внешним API.
После завершения обновления и OSV возвращаются обычные квоты. Их текущие счётчики
не обнуляются: новые импорты могут ждать окончания часового окна.

Сначала обновить выборку через административный `scripts.report_stage5` в
контейнере `checks` с томом `docs/evidence/stage5:/evidence`. Полные наборы лежат в
`cohorts/<sha256>.json`. Каждый отчёт получает `cohort.ref.json` с относительным
путём к данным и их SHA-256. Генератор проверяет хеш и монтирует соответствующий
файл в k6 по пути `/data/cohort.json`. Старые локальные каталоги с исходным
`cohort.json` также поддерживаются. Генератор читает сохранённые ID из всей
выборки. Каталог включает три сортировки и первые десять cursor-страниц; поиск —
точные имена и общий термин `python`. Холодный прогон не выполняет предварительных
запросов каталога. Приватные 5% — только чтение двумя изолированными dev-акторами;
это не проверка будущей авторизации этапа 6. Нагрузка не запускает импорт.
