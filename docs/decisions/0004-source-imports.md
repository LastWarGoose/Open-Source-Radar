# 0004. Сбор источников и восстановление импорта

Дата: 17 ноября 2026. Дополняет контракты этапа 2.

## Владение и запуск

`requestImport(requestKey, targets)` принимает 1–20 пакетов, опционально конкретную
версию. Без версии берётся текущий релиз из PyPI. Это ограниченный сбор выбранных
версий, не загрузка всей истории и не массовый импорт 10 000 пакетов.

Catalog атомарно создаёт ImportJob и технические записи source_work. Последние
совмещают постоянное задание и outbox: до успешного завершения они доступны для
повторной доставки. Состояние не хранится в Celery result backend.

Catalog worker получает PyPI project JSON и при необходимости JSON выбранной
исторической версии. Зависимости берутся именно из выбранной версии. Данные,
requirements и checkpoint фиксируются одной транзакцией. Затем worker через
защищённые GraphQL-mutation создаёт задания в Repositories и Security. UUID
производных заданий детерминирован от задания Catalog, поэтому повтор передачи
безопасен. После checkpoint повтор не требует нового запроса к PyPI.

ImportJob с source=PYPI и status=succeeded означает сохранение PyPI и постановку
обогащения. Это **не** обещание успешного GitHub/OSV. Их результаты доступны через
`repositoryImportJob`, `securityImportJob`, `githubFreshness` и `Release.scan`.
Скрипт живой приёмки ожидает успеха всех трёх владельцев.

Каждый worker имеет только пароль своей БД. Межсервисных SQL-запросов нет.
Общие source_work/source_state/source_quota — технические таблицы транспорта
и проверки свежести, развёрнутые миграциями в каждой базе отдельно. Предметные
модели, адаптеры и запись результатов остаются в сервисах-владельцах.

## Доставка и повторы

- Три очереди `catalog.imports`, `repositories.imports`, `security.imports`;
  отдельные workers, concurrency=1 и prefetch=1. Probe worker слушает только probes.
- Один Beat с PostgreSQL session advisory lock. При потере соединения с lock он
  завершается. Каждые 10 секунд публикует технический запрос проверки очереди
  каждому владельцу; он не создаёт бесконечные новые импорты пакетов.
- Диспетчер выбирает due-задания с блокировкой SKIP LOCKED, использует persistent
  delivery и publisher confirms. При ошибке публикации транзакция откатывается.
  Незавершённое задание публикуется повторно после двух минут.
- Worker получает session advisory lock на UUID. Повтор завершённого задания
  ничего не меняет. При убийстве процесса блокировка освобождается; checkpoint
  и данные остаются в БД. Старое задание не перезаписывает более новую проверку.
- До 3 HTTP-попыток на временную сетевую ошибку/выбранные 5xx с jitter.
  До 5 попыток задания, soft/hard time limit 240/270 секунд.
  Для квот нет немедленного HTTP-retry; due-time сохраняется в PostgreSQL.
  Локальная квота не расходует счётчик попыток, но автоматическое ожидание
  ограничено сутками с момента создания.
- `resumeImport(id)` повторно ставит failed-части PyPI, сохраняя checkpoint.
  Для нового обогащения после окончательного отказа GitHub/OSV создаётся новый
  requestImport с новым requestKey; upsert сохраняет идентичность предметных записей.

## Ограничения источников

HTTPX: connect 5 с, остальные HTTP timeout 15 с, одна connection на адаптер.
Каждая сессия ограничена 100 HTTP-запросами и 8 MB на ответ. По хостам разрешены
только pypi.org, api.github.com, api.osv.dev, HTTPS; перенаправления разрешены
только на тот же хост, не более трёх.

Консервативные локальные бюджеты на час: PyPI 120, GitHub 30, OSV 300.
Минимальные интервалы: 0,5 / 1 / 0,2 секунды. Расход и блокировки квоты
фиксируются в собственной PostgreSQL, поэтому перезапуск worker не сбрасывает их.
Retry-After (секунды/HTTP-date), GitHub reset и primary/secondary rate limit
переносят следующую попытку. Обычные 401/403/404 не повторяются автоматически.

Токен GitHub необязателен для небольшого публичного запуска и доступен только
repositories-importer. Он не передаётся Web, GraphQL-клиенту и другим workers.

GitHub-ссылки берутся из project_urls/home_page PyPI, не угадываются по имени
пакета. Принимаются только канонические HTTPS-ссылки на репозиторий, максимум 5.
GitHub API подтверждает публичный репозиторий; его числовой ID используется как
стабильный ключ при переименовании. Подтверждение ссылки не означает общность
владельцев PyPI и GitHub. Удалённые/неподтверждаемые ссылки не считаются VERIFIED.

OSV запрашивается по PyPI-имени и конкретной версии через querybatch; продолжается
next_page_token, затем запрашиваются подробности каждого advisory. Лимиты —
10 страниц и 50 идентификаторов; превышение даёт явную ошибку, не неполный SUCCESS.
Withdrawn исключаются, алиасы объединяются. В текущей модели сохраняются
идентификатор, summary, aliases, происхождение и время; полный исходный JSON
advisory пока не является частью модели.

## Свежесть и границы этапа

Для PyPI/GitHub доступны UNKNOWN, SUCCESS, STALE, FAILED, время попытки и последнего
успеха. Успех старше суток читается как STALE. Аналогичная семантика применяется
к VersionScan. Ошибка после успеха сохраняет прежние данные и findings. Пустой
успешный ответ OSV означает отсутствие найденных совпадений, а не «пакет безопасен».

Публичный Web остаётся демонстрацией этапа 0. Подключение настоящего каталога,
карточек и статусов к интерфейсу относится к этапу 4. Аккаунтный доступ и панель
импорта ещё не реализованы; действует явная локальная dev-admin защита.
Обычный CI использует синтетические HTTP-ответы, живой smoke запускается отдельно.
