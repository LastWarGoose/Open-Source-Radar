# Инструкции для работы над Open Source Radar

Проект относится к Work With GraphQL. Следуйте актуальным указаниям пользователя и более приоритетным инструкциям среды. Этот файл задаёт проектные соглашения; он не предоставляет разрешение на внешние публикации, отправку сообщений или изменения платной инфраструктуры.

## Перед изменениями

1. Прочитать README.md, docx/ARCHITECTURE.md и текущий этап docx/DEVELOPMENT_PLAN.md.
2. Прочитать вложенные AGENTS.md в затрагиваемых каталогах, если они появятся.
3. Проверить состояние рабочей копии. Сохранять чужие и незавершённые изменения.
4. Выбрать критерии проверки из docx/TEST_PLAN.md, соответствующие задаче.
5. Если работа делегирована, соблюдать границы и правила docx/SUBAGENTS.md.

Общаться с пользователем по-русски. Идентификаторы, имена файлов, код и имена GraphQL-операций — на английском. Пользовательская документация — по-русски. Не выдавать запланированное за реализованное.

## Инварианты архитектуры

- Прикладное взаимодействие сайта с backend — только через общий GraphQL API. Server Components Next.js также обращаются к GraphQL; не подключать их к PostgreSQL или внешним источникам.
- FastAPI размещает Strawberry; не создавать параллельный REST API каталога, подборок или импорта. Health/readiness, метрики и необходимый callback внешнего провайдера входа — технические исключения, которые надо документировать.
- Federation реальная: отдельные подграфы и запросы, объединяющие данные разных владельцев. Не подменять её монолитом с несколькими папками.
- Данные принадлежат сервису. Запретить чтение чужих таблиц, межсервисные SQL JOIN и общие ORM-модели предметных сущностей. Использовать GraphQL entity references.
- RabbitMQ — брокер Celery. Redis — кеш и, если потребуется, временные результаты задач. Не добавлять Kafka без отдельного решения о сценарии её использования.
- Сбор данных идёт в фоне. Чтение каталога не должно инициировать синхронное обращение к PyPI/GitHub/OSV.
- Все длинные операции запускаются задачами с сохранённым состоянием и возвращают job ID.

## GraphQL и данные

- Сначала согласовать схему, владельцев полей и ключи Federation; затем писать резолверы и клиентские операции.
- Использовать именованные операции, переменные и сгенерированные типы. Не вставлять пользовательский ввод в текст GraphQL.
- Списки ограничены пагинацией; стартовый максимум страницы — 100. Для вложенных списков ограничения также обязательны.
- Cursor включает позицию в устойчивом порядке и уникальный дополнительный ключ. Не обещать переход по номерам страниц при cursor-пагинации.
- DataLoader создаётся на запрос и в контексте пользователя; не делить кеш приватных данных между запросами.
- Не выполнять синхронный сетевой/SQL-ввод-вывод внутри асинхронного резолвера.
- Нормализовать имена PyPI; сохранять исходные идентификаторы источников. Пакет и репозиторий не связаны как строго один-к-одному.
- Сохранять происхождение и время получения данных. Отличать «не проверено», «источник недоступен» и «проверено, совпадений нет».
- Не обозначать библиотеку безопасной из-за пустого ответа OSV. Сохранять условия зависимостей, extras и ограничения версий; не выдавать их за разрешённое дерево установленного окружения.

## Фоновые операции

- Установить HTTP-таймауты, лимиты параллелизма и отдельные бюджеты запросов для каждого источника.
- Уважать Retry-After и заголовки лимитов. Не повторять безусловно все 4xx; 403 сначала классифицировать по ответу источника.
- Tenacity обрабатывает краткие временные сбои HTTP. Celery может перепланировать целую задачу. Ограничивать суммарное число попыток и время; не допускать перемножения бесконтрольных retries.
- Задачи идемпотентны; уникальные ограничения и upsert защищают от дублей. Проверять повторную доставку и сбой после commit до ack.
- Хранить checkpoint и статус импорта в PostgreSQL. Кеш и Celery result backend не являются источником истины для прогресса.
- Настройка ack, подтверждения публикации, durable queues и восстановления фиксируется и тестируется; наличие RabbitMQ само по себе не даёт exactly-once.
- Повторная постановка заданий восстанавливается по журналу jobs/outbox; запись в БД и публикация в брокер не считаются одной атомарной операцией.
- Не скачивать, не устанавливать и не исполнять код пакетов для сбора метаданных.

## Доступ и секреты

- Проверять права на приватные сущности в сервисе-владельце, даже если шлюз уже проверил сессию.
- Не доверять заголовку user ID из публичного запроса. Внутренний контекст пользователя защищён, подграфы не выставлены в публичный доступ.
- Проверять CSRF/Origin для cookie-аутентификации и мутаций; политика CORS явная.
- Ссылки на репозитории нормализуются, источники ограничены allowlist; не разрешать произвольные URL загрузки и не переходить на приватные адреса через редиректы.
- Секреты не попадают в Git, логи, трассировки, снимки тестов и клиентский bundle. В .env.example только названия и фиктивные значения.
- Данные пользователя не смешиваются в общем кеше; удаление/изменение подборки требует проверки владельца.

## Разработка и проверки

- Версии фиксировать в lock-файлах; образы — конкретными версиями, при выпуске желательно digest. Не писать latest в воспроизводимом окружении.
- Изменение БД оформлять миграцией Alembic у соответствующего сервиса.
- Не скрывать ошибки через any, blanket except, отключение линтеров или пропуск теста без объяснения.
- Проверять поведение и риски изменения; не добавлять тесты, копирующие реализацию. Для документации достаточно проверок ссылок и согласованности.
- Реальные команды брать из существующих конфигураций. Не утверждать, что вымышленные команды или отсутствующие тесты прошли.
- PR-проверки не зависят от живых внешних API. Живые проверки — отдельный ограниченный запуск.
- После работы сообщить: что изменено, чем проверено, что не проверено и почему. Обновить статус этапа только при наличии подтверждения.

## Завершение задачи

По указанию пользователя в конце каждой задачи с изменениями создать коммит с результатами этой задачи и отправить текущую рабочую ветку в репозиторий `LastWarGoose/Open-Source-Radar` на GitHub. Сверить хеш отправленного коммита с удалённой веткой.

Задача готова, когда выполнены её критерии приёмки, пройдены релевантные проверки, обновлены схема/документация/миграции и явно описаны оставшиеся ограничения. Не начинать следующий большой этап автоматически, если пользователь ограничил работу текущим этапом.
