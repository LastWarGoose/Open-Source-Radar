# Команда Open Source Radar

Основной агент ведёт задачу как архитектор. Пять профилей субагентов хранятся в [`.codex/agents/`](../.codex/agents/), короткие инструкции по каждой роли — в [`.agents/skills/`](../.agents/skills/). Архитектор назначает только роли, нужные конкретной задаче. Если среда не поддерживает делегирование, он проходит те же шаги последовательно и указывает, какие проверки выполнил сам.

| Роль | За что отвечает | Навык |
|---|---|---|
| Архитектор | Критерии приёмки, контракты между частями системы, владельцы файлов, интеграция и итоговое решение | [radar-architect](../.agents/skills/radar-architect/SKILL.md) |
| [Фронтенд](../.codex/agents/frontend.toml) | Страницы и клиентские операции в `apps/web/`, доступность и состояния интерфейса | [radar-frontend](../.agents/skills/radar-frontend/SKILL.md) |
| [Бэкенд](../.codex/agents/backend.toml) | Четыре подграфа в `services/`, включая импорт OSV, а также `gateway/`, миграции и фоновые задачи | [radar-backend](../.agents/skills/radar-backend/SKILL.md) |
| [QA](../.codex/agents/qa.toml) | Независимая проверка пользовательских сценариев, контрактов и регрессий на тестовом стенде | [radar-qa](../.agents/skills/radar-qa/SKILL.md) |
| [Ревью](../.codex/agents/review.toml) | Ревью diff и доказательств QA, решение по каждому замечанию | [radar-review](../.agents/skills/radar-review/SKILL.md) |
| [Безопасность](../.codex/agents/security.toml) | Защитная проверка изменений в доступе, сессиях, приватных данных, внешних источниках и секретах | [radar-security](../.agents/skills/radar-security/SKILL.md) |

## Передача работы

Архитектор передаёт исполнителю цель, область файлов, входной контракт, критерии приёмки и ограничения стенда. Фронтенд и бэкенд могут работать параллельно после согласования схемы. В общей рабочей копии каждый изменяемый путь имеет одного владельца. Общие файлы — supergraph, lock-файлы, Compose, CI, `infra/` и `packages/python-common/` — архитектор берёт на себя или явно назначает исполнителю.

Исполнитель возвращает список файлов, версию изменения, команды и результаты проверок. Версию можно обозначить коммитом или точным снимком diff с базовым коммитом. Для изменений авторизации, приватных данных, внешних источников и секретов архитектор подключает безопасность до итогового ревью. В отчётах используют обезличенные примеры и очищенные логи.

## Цикл приёмки

1. **QA → ревью.** QA проверяет собранное изменение по критериям задачи. Для сбоя указывает ID, версию, шаги, ожидаемое и фактическое поведение. Ревью получает отчёт и при успешных проверках.
2. **Ревью → владелец.** Ревьюер сверяет diff, отчёт QA и относящиеся к задаче замечания безопасности. Блокирующий дефект получает владельца и проверяемое условие закрытия. Если причина в тесте, исправление получает QA, если в продукте — фронтенд или бэкенд. Спор о контракте решает архитектор.
3. **Исправление → QA → ревью.** Владелец возвращает новую версию с ID замечания. QA повторяет исходный сценарий и связанные проверки. Ревьюер сверяет исправление с результатом на этой версии и закрывает ID либо возвращает его владельцу.
4. **Ревью → архитектор.** Архитектор принимает результат, когда QA подтвердил критерии, ревью приняло ту же версию и открытых блокирующих замечаний нет. Если обязательная проверка недоступна или повторяется сбой без новых данных, цикл получает статус «заблокировано». Архитектор фиксирует причину, владельца следующего шага и условие возобновления.

Например, QA обнаружил, что после фильтрации логотип прокручивает страницу мимо RADAR. Ревьюер передаёт фронтенду ID и условие закрытия — видна верхняя граница RADAR, фильтр сохранён. После исправления QA повторяет тот же переход, а ревьюер закрывает замечание по проверенной версии.

Критерии выбирают из [плана проверок](TEST_PLAN.md). Приёмку, коммит и отправку ветки координирует архитектор по [правилам проекта](../AGENTS.md).
