# Роли и порядок работы субагентов

Этот файл описывает организацию будущей разработки. Он не является конфигурацией конкретного runtime и сам по себе не запускает агентов. Делегировать только когда это разрешено пользователем и инструкциями среды. Если параллельные агенты недоступны, роли выполняются последовательно основным агентом.

## Роли и зоны ответственности

| Роль | Основные пути | Результат |
|---|---|---|
| Coordinator / Integrator | Корневые документы, контракты, общие настройки | Разбивка задач, решения, последовательная интеграция и итоговые проверки |
| GraphQL / Federation | `gateway/`, `packages/graphql/`, `tests/contract/` | Композиция схемы, entity keys, ограничения, контракты и совместимость подписок |
| Catalog / PyPI | `services/catalog/` | Каталог, версии, requirements, импорт PyPI, проекция сортировки |
| Repositories / GitHub | `services/repositories/` | Сопоставление репозиториев, GitHub-адаптер, квоты и публикация изменений |
| Security / OSV | `services/security/` | Проверки версий, advisory и алиасы, корректные статусы OSV |
| Workspace / Auth | `services/workspace/` | Учётные записи, доступ, подборки, отслеживание и уведомления |
| Frontend | `apps/web/` | Страницы, GraphQL-операции, UI, доступность и состояния |
| Platform / Observability | `infra/`, CI-конфигурация, Dockerfiles по согласованию | Окружение, RabbitMQ/Celery, telemetry и воспроизводимый запуск |
| QA / Reviewer | `tests/e2e/`, `tests/load/`, отчёты проверок | Независимые сценарии, проверка требований, диагностика регрессий |

Это перечень компетенций, а не требование запускать девять агентов одновременно. Начальный предел — 2–3 независимых исполнителя плюс координатор, в пределах лимитов среды. У каждой изменяемой области в конкретный момент один владелец.

## Задачи с общим владением

- Корневые lock-файлы, Compose, общие зависимости, supergraph и корневые инструкции изменяет назначенный интегратор или один явно выбранный исполнитель.
- Владелец подграфа предлагает SDL, GraphQL-роль проверяет совместимость, интегратор обновляет общий контракт. Не редактировать одну схему одновременно.
- Dockerfile сервиса согласуется с владельцем сервиса; Platform не переписывает его незаметно.
- Тесты внутри сервиса принадлежат его исполнителю. QA может читать и рецензировать их; изменения в том же файле делаются после передачи владения.
- `packages/python-common/` — общий код: технические изменения сначала согласовать; не переносить туда модели предметной области ради удобства.

## Карточка поручения

Каждая задача содержит:

1. Цель и связанный этап/ID требований.
2. Разрешённые пути и текущего владельца общих файлов.
3. Входные контракты: схема, IDs, ошибки, события, переменные окружения.
4. Критерии приёмки и конкретные релевантные проверки.
5. Ограничения: внешние запросы, секреты, миграции, объём данных.
6. Формат отчёта: изменённые файлы, выполненные проверки, результаты, риски, требуемая интеграция.

Пример: «Реализовать нормализацию PyPI и идемпотентный импорт проекта в services/catalog. Не менять gateway и общие lock-файлы. Пройти тесты нормализации, повторного payload и восстановления checkpoint. Живой массовый импорт не запускать в рамках этой задачи».

## Порядок параллельной работы

1. Координатор фиксирует контракты, зависимости и владельцев путей.
2. Исполнители работают в отдельных ветках/worktree, если это поддерживается. При общей рабочей копии области файлов должны быть непересекающимися.
3. При необходимости общего изменения исполнитель передаёт предложение координатору, а не изменяет чужую область.
4. Исполнитель выполняет локальные проверки и передаёт отчёт с точным списком файлов.
5. Координатор интегрирует последовательно, затем выполняет composition, генерацию типов и релевантный сквозной сценарий.
6. QA проверяет результат независимо. Статус этапа обновляет координатор после проверки доказательств.

Не отменять чужие изменения, не выполнять массовый reset/clean и не переписывать историю без явного разрешения. Не скрывать конфликты заменой файлов целиком. Секреты и приватные payload не пересылать в сообщениях агентов.

## Рекомендуемые группы работ

| Когда | Возможная параллельность | Ограничение |
|---|---|---|
| Этап 0 | Coordinator + GraphQL, Frontend после минимального контракта | Совместимость важнее числа исполнителей |
| Этапы 1–2 | Platform и владельцы моделей | Общие конфигурации интегрируются одним владельцем |
| Этап 3 | Три адаптера источников | Общий формат Job, retry policy и IDs уже согласованы |
| Этап 4 | Frontend и подготовка проекции/контрактных тестов | Не менять используемую SDL без синхронизации |
| Этапы 6–7 | Workspace, Platform и QA | Auth-контракт и redaction согласованы до интеграции |

## Условие приёмки работы субагента

Код существует, соответствует контракту, проверен указанным способом, не затрагивает чужие изменения, а ограничения явно перечислены. «Должно работать» и «тесты не запускал, но ошибок не видно» не означают готовность. Если окружение блокирует тест, статус остаётся «не проверено» с причиной.
