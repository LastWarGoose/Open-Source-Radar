# Архитектура Open Source Radar

Статус: этапы 0–6 реализованы. Работают публичный каталог, карточки и сравнение, Gateway, четыре подграфа Catalog/Repositories/Security/Workspace, изолированные PostgreSQL, поиск, cursor-пагинация, DataLoader, RabbitMQ/Redis и сбор PyPI/GitHub/OSV отдельными workers с единственным Beat. Реальные и синтетические записи различаются по происхождению. Ограниченная очередь кампании завершила 10 000 успешных импортов по сохранённому манифесту; на наполненной базе проверены SQL, baseline, stress и чтение при фоновом обновлении. Локальные аккаунты, личные подборки, уведомления и административная панель реализованы. В профиле observability работают Prometheus, Grafana, Tempo и Loki. Шлюз ограничивает стоимость и частоту операций. Контекст фоновой задачи сохраняется вместе с заданием. [Настройки и границы локального стенда](../docs/decisions/0008-observability.md). [Аккаунты и доступ](../docs/decisions/0007-accounts.md). [Результаты этапа 5](../docs/evidence/stage5-2026-11-17.md), [версии](../docs/decisions/0001-versions.md), [контракты](../docs/decisions/0003-domain-contracts.md), [массовый импорт](../docs/decisions/0006-bulk-import.md).

## Требования и технические решения

| Требование | Решение |
|---|---|
| GraphQL между frontend и backend | Один публичный endpoint Hive Gateway; Next.js обращается только к нему |
| Автосбор из трёх источников | Адаптеры PyPI, GitHub и OSV; Celery workers и Beat |
| Не менее 10 000 записей | 10 000 уникальных нормализованных пакетов; отдельные метрики обогащения |
| Вложенность и динамические операции | Связи Package → Releases → Vulnerabilities и Package → Dependencies → Package → Repository; variables, fragments, directives |
| Фильтры, поиск, сортировка, пагинация | PostgreSQL FTS/pg_trgm; стабильная cursor-пагинация |
| Производительность и устойчивость | Индексы, DataLoader, ограниченный кеш, фоновые обновления, восстановление задач |
| Контроль нагрузки и наблюдаемость | Ограничения частоты/стоимости операций, лимиты источников, OTel, метрики и логи |
| GraphQL Federation | Четыре самостоятельных подграфа, составленная общая схема и межсервисные entity references |

## Владение данными и Federation

- Catalog владеет Package с глобальным стабильным ключом `id`, нормализованным `name` и `ecosystem=PyPI`. Release имеет отдельный стабильный ID и исходную версию.
- Repositories расширяет Package полем связей с Repository. Репозиторий может соответствовать нескольким пакетам, пакет может иметь несколько заявленных ссылок. Ссылки проверяются и получают статус достоверности сопоставления.
- Security расширяет Release результатом проверки уязвимостей. Запись Vulnerability хранит собственный ID OSV и алиасы. Один advisory не размножается из-за нескольких затронутых версий.
- Workspace хранит ссылки на Package/Release по ID; для вывода метаданных возвращает entity references. SQL foreign key через базы сервисов отсутствует.
- В локальном окружении один PostgreSQL с отдельными базами и ролями четырёх сервисов. Пользователь приложения не получает права читать базы соседей. Это упрощение инфраструктуры, а не отказоустойчивый кластер.
- Общие библиотеки содержат транспорт, телеметрию и технические ошибки. Предметные ORM-модели и миграции остаются у владельца.

При сбое подграфа допустимые nullable-поля возвращают частичные данные с GraphQL errors. UI показывает недоступность секции. Nullability и распространение ошибки проверяются интеграционными тестами.

## Схема потока данных

Чтение: браузер или Next.js Server Component → Hive Gateway → нужные подграфы → принадлежащие им PostgreSQL/Redis → GraphQL-ответ. Источники не вызываются при обычном чтении страницы.

Запуск импорта: административная mutation → запись Job и outbox у сервиса-владельца → dispatcher → RabbitMQ → worker → внешний API → транзакционное сохранение данных и checkpoint. Dispatcher может повторно публиковать; worker должен безопасно обработать повтор.

Изменения статуса: сохранённое состояние Job → сигнал обновления → subscription через подграф и шлюз → UI. Событие — повод перечитать состояние, а не единственная копия прогресса. При переподключении клиент выполняет query текущего состояния. Redis Pub/Sub допустим для этих временных сигналов, но не для гарантированной доставки заданий или истории уведомлений.

Если публикация события обязана переживать сбой, использовать журнал/outbox и подтверждаемую доставку; не полагаться на обычный Pub/Sub.

## Внешние источники и качество

| Источник | Получение и назначение | Ограничения модели |
|---|---|---|
| PyPI | Index API для кандидатов; JSON API для метаданных проектов и выбранных релизов | Метаданные издателя могут быть неполными; сохранять статус полноты |
| GitHub | Нормализованные project URLs из PyPI, затем API репозитория | Не все пакеты имеют GitHub; не угадывать связь по имени |
| OSV | Запросы по ecosystem, имени, версии; batch для набора версий, затем детали advisory | Отсутствие совпадений не является гарантией безопасности |

В первом импорте собираем метаданные актуального стабильного релиза, список доступных версий и обогащаем выбранные версии. Детальные данные каждой исторической версии не обязательны для первого наполнения. Политика выбора prerelease/yanked и отсутствие стабильной версии фиксируются до массового импорта. Сравнение версий и нормализация используют правила Python packaging, а не строковую сортировку.

Объявленная зависимость хранит исходное requirement, имя, specifier, extras и marker. Это не lockfile: без конкретного Python, платформы и разрешения зависимостей нельзя утверждать, какая транзитивная версия будет установлена. UI подписывает граф как граф объявленных зависимостей.

Источник, внешний ID, время получения, время последней успешной проверки и статус импорта сохраняются. Для обновлений используем ETag/Last-Modified там, где источник их поддерживает. Режим хранения сырых ответов ограничен сроком и размером; токены и персональные данные туда не попадают.

Предлагаемые интервалы, уточняемые по квотам: актуальные метаданные PyPI/GitHub — раз в сутки, OSV для отслеживаемых версий — раз в 6 часов, остальной каталог — фоновыми порциями. Добавить jitter и не ставить весь каталог одновременно. На старте снять бюджет запросов и оценку длительности импорта. 10 000 строк не предполагают 10 000 запросов каждую минуту.

## API и сайт

Полная SDL сохранена в `packages/graphql/`. Реализованы `packages`, `package`,
`release`, `repository`, `vulnerability`, `myCollections`, `collection`,
`myNotifications`, защищённый `importJobs` и технические операции этапов 0–1.
Следующий список описывает целевой API первой версии, включая ещё не реализованные операции:

- `packages(filter, search, sort, first, after)`, `package(id)`, `comparePackages(ids)`.
- `myCollections`, `myNotifications`, `importJobs` — с проверкой доступа.
- `createCollection`, `addPackageToCollection`, `removePackageFromCollection`, `followPackage`, `markNotificationRead`.
- `requestImport`, `retryImport` — только администратор; возвращают Job.
- `importProgress(jobId)` — subscription с проверкой прав при подписке и политикой истечения сессии.

Публичный каталог индексируется; приватные страницы не индексируются. Метаданные страницы и canonical URL формируются явно. Фильтры/сортировка отражаются в URL. Состояния: loading, empty, partial, error, stale и unknown. Даты хранятся в UTC, отображаются с выбранным часовым поясом. Полнота источников и время обновления видимы пользователю.

Пагинация по умолчанию 20, максимум 100 записей. Порядок, например `updated_at DESC, id DESC`. Курсор кодирует необходимые значения и привязан к сортировке/фильтрам; не даёт прав доступа. Изменение фильтра сбрасывает cursor. Для изменяющегося набора документируем поведение; не обещаем снимок без отдельного механизма snapshot.

На первом этапе фильтры и сортировки выполняются по полям владельца Catalog. Для сортировки всего каталога по GitHub stars нужна отдельная локальная проекция в Catalog: обновляемые Repository-события содержат версию и время, обработчик идемпотентен, существует периодическая сверка. Нельзя сортировать уже полученную страницу в браузере и выдавать это за глобальную сортировку. Вариант проекции и её допустимое отставание реализуются перед включением сортировки по звёздам.

## Производительность, нагрузка и доступ

- Индексы по реальным фильтрам и порядку; планы SQL проверяются на наполненном наборе.
- Request-scoped DataLoader и ограниченная вложенность. Лимит глубины дополняется стоимостью списков и общим бюджетом времени.
- Стартовый кандидат ограничения глубины — 8; окончательный лимит выводится из реальных разрешённых операций. Отдельно ограничиваются aliases, размер batch/variables, длительность запроса и число активных subscriptions.
- Rate limiting по IP/пользователю и отдельные квоты административных mutation. Публичный интерфейс не принимает произвольные источники загрузки.
- Общий кеш только для публичных данных; приватные ответы изолированы. Инвалидация после обновления и TTL документируются; при недоступном Redis чтение идёт в БД с ограничением нагрузки.
- Анонимное чтение; роли user/admin. Выбраны локальные аккаунты с паролем и одноразовым кодом восстановления. Реализованы HttpOnly/SameSite-cookie (Secure при HTTPS), CSRF/Origin-проверки и отзыв сессий.
- Токены внешних API остаются в workers. Внешний HTML/Markdown описаний отображается с безопасной обработкой; ссылки не становятся произвольными server-side fetch.

## Устойчивость

Tenacity: сетевые сбои, выбранные 5xx и корректно обработанный 429; ограничение попыток и полного времени. Для длительного rate limit задача перепланируется вместо удержания worker в sleep.

Celery/RabbitMQ: durable topology, persistent messages, publisher confirms, осознанный late ack и политика requeue. Конкретная конфигурация зависит от закреплённых версий и проверяется kill/restart-тестом. Исключения валидации не повторяются бесконечно; ошибочные задания получают failed и доступны для административного разбора.

PostgreSQL: уникальные ключи, upsert и транзакции. Checkpoints возобновляют импорт. Jobs/outbox восстанавливает публикацию после сбоя; версии обновлений защищают от записи устаревшего результата поверх нового.

Docker Compose с volumes и healthchecks обеспечивает воспроизводимость и восстановление процессов на одной машине. Он не переживает потерю всей машины. Репликация PostgreSQL, RabbitMQ quorum queues на нескольких узлах, балансировка реплик и их испытания — отдельный этап после выбора среды; не заявлять HA до его выполнения.

## Наблюдаемость и поставка

Передавать trace context через gateway, HTTP и заголовки фоновых задач. Для долгого отложенного запуска использовать связанный trace/span, не оставлять один span открытым часами. Не включать необработанные токены, variables и тела ответов в телеметрию.

Метрики: задержка операций и ошибки GraphQL (включая HTTP 200 с errors), SQL-запросы, очередь и возраст задач, retries, ошибки/квоты источников, свежесть и полнота данных, cache hit, активные subscriptions. Labels ограниченной кардинальности: не использовать package ID, user ID и произвольный текст запросов.

Compose: базовые сервисы, отдельный профиль `observability`; опциональный профиль инструментов разработки. Собрать миграции как явный шаг, не запускать конкурирующие миграции каждой репликой. CI выполняет проверки схемы и локальные тесты без доступа к живым источникам. Секреты только через окружение/secret store; lock-файлы и образы закреплены.
