## Уровни проверки

| Уровень | Инструменты | Что покрывает |
|---|---|---|
| Статический | Ruff, mypy, ESLint, TypeScript, GraphQL Codegen | Ошибки типов, стиль, соответствие клиентских операций схеме |
| Модульный | pytest, Vitest | Нормализация, правила фильтрации/курсоров, разбор данных, retry-классификация |
| Интеграционный | pytest + реальные тестовые PostgreSQL/RabbitMQ/Redis | Миграции, upsert, задачи, транзакции, права, доставка |
| Контрактный | Composition и GraphQL integration tests | Общая схема, entity keys, nullability, совместимость операций |
| Компонентный | React Testing Library | Формы, доступность, загрузка и ошибки |
| Сквозной | Playwright | Пользовательские сценарии через gateway |
| Нагрузочный | k6 | Задержки, пропускная способность, ошибки, ограничения |

Использовать fixtures внешних API с явной датой/происхождением и удалёнными секретами. Тесты проверяют ожидаемое поведение, не конкретное внутреннее устройство функции. Каждый тест использует независимые данные и очищает только свои тестовые ресурсы.

## Критические сценарии данных и API

- `Foo_Bar`, `foo.bar` и `foo-bar` нормализуются по правилам PyPI и не создают дубликаты.
- Версии сортируются по правилам packaging; prerelease/yanked/невалидные метаданные обрабатываются по принятой политике.
- Requirement с marker/extras/specifier не теряет условие и не выдаётся за выбранную установленную версию.
- Один репозиторий связан с несколькими пакетами без размножения Repository; недостоверная ссылка помечается, не угадывается.
- Неизвестный результат OSV отличается от успешной проверки без совпадений. Алиасы advisory не завышают счётчик.
- Повтор одного payload, повтор задачи и повтор страницы импорта не увеличивают число уникальных записей.
- Устаревший результат worker не затирает более свежие данные.
- Cursor: первая/последняя/пустая страница, равные sort keys, неверный курсор, смена фильтра, максимум размера. В неизменном наборе нет пропусков и дублей.
- Сортировка по stars использует весь каталог и отражает согласованное состояние проекции; проверить out-of-order события и reconciliation.
- Вложенный запрос из нескольких подграфов возвращает правильные связи. Для 20 и 100 элементов число однотипных SQL-запросов не растёт линейно с числом элементов; исходный бюджет фиксируется для каждой операции.
- Недоступный подграф возвращает ожидаемые nullable-секции и errors; обязательные поля и null bubbling проверяются отдельно.
- Сервер отказывает операции сверх ограничений до дорогого исполнения; aliases и вложенные списки учитываются в стоимости.

## Браузер и доступ

1. Открыть каталог, найти пакет, применить фильтры, перейти вперёд/назад; URL восстанавливает состояние после перезагрузки.
2. Открыть карточку и связанные сущности, проверить stale/unknown/partial состояния.
3. Сравнить несколько пакетов; превышение лимита имеет понятное сообщение.
4. Пользователь A создаёт подборку; B и анонимный пользователь не могут её прочитать/изменить подбором ID.
5. Проверить вход/выход, истечение сессии, CSRF/Origin, приватный кеш SSR и отсутствие токенов в bundle.
6. Администратор запускает импорт и видит прогресс; обычный пользователь получает отказ. Повторный клик не создаёт неконтролируемое дублирование.
7. Разорвать subscription, восстановить соединение, query возвращает актуальный Job. Закрытая/истёкшая сессия не продолжает получать приватные события.
8. Проверить клавиатуру, focus, подписи, ошибки форм, zoom 200%, отсутствие ненужного горизонтального скролла на ширине 360/768/1440 px. Сложные таблицы имеют управляемый контейнер прокрутки.
9. Проверить публичные metadata/canonical и запрет индексации приватных страниц. Анализаторы доступности дополняются ручной проверкой.

## Источники и контроль повторов

| Сбой | Ожидаемое поведение |
|---|---|
| Timeout/временный 5xx | Ограниченные retries с backoff/jitter, затем сохранённая ошибка или перепланирование |
| 429 с Retry-After | Уважение задержки и общей квоты; без потока немедленных повторов |
| 401 или неверный credential | Прекращение бессмысленных повторов, скрытый секрет, диагностируемая ошибка |
| 403 | Различение rate limit и отказа в доступе; решение по ответу источника |
| 404 | Явное отсутствие ресурса/снятая связь; не бесконечный retry |
| Невалидный JSON/схема | Failed/quarantine с причиной; существующие валидные данные сохранены |
| Длительное отключение источника | Сайт читает последнюю сохранённую версию; UI показывает свежесть и проблему |

Проверять суммарный бюджет попыток HTTP и задачи. В тестах использовать управляемое время; не ждать реальные минуты backoff. Живые проверки выполнять отдельно с небольшим запросным бюджетом и реальными credentials, без стресс-тестирования чужих API.

## Испытания отказов

| Сценарий | Приёмка |
|---|---|
| Worker остановлен до commit | Задача может повториться, checkpoint не перескакивает необработанные данные |
| Worker остановлен после commit до ack | Повторная доставка не создаёт дубликаты и не портит результат |
| Брокер недоступен во время постановки | Job/outbox сохранён; публикация возобновляется после восстановления |
| Перезапуск RabbitMQ с настроенной persistence | Принятые и подтверждённые persistent задания восстановлены согласно конфигурации |
| Недоступен Redis | Публичное чтение выполняется через БД в пределах бюджета; прогресс jobs не потерян |
| Недоступен один подграф | Независимые разделы доступны; зависимые показывают понятный частичный отказ |
| Перезапуск scheduler | Нет множества одинаковых периодических запусков; один активный Beat |
| Бэкап и восстановление PostgreSQL | В отдельной тестовой базе восстановлены контрольные записи и связи |

Измерять время восстановления, число повторов и сохранность данных. Потеря всего хоста и многоузловый failover не считаются покрытыми тестом перезапуска контейнера.

## Нагрузочная методика и стартовые цели

Перед запуском записать CPU, RAM, диск, ОС, версии образов, commit, число реплик, размеры данных и состояние кеша. Нагрузку генерировать отдельно от приложения, если это возможно; иначе явно указать совместное использование ресурсов. База содержит ≥10 000 пакетов и связанные сущности. Внешние вызовы отключены/замоканы; нагрузка только на нашу систему.

Базовый профиль: 20 виртуальных пользователей, одна итерация — одна операция и пауза 1 секунду; смесь 60% каталог, 25% карточка с федеративными полями, 10% поиск, 5% личные операции. Тестовые пользователи изолированы. Прогрев 2 минуты, измерение 10 минут; фактический RPS записывается, а не приравнивается к числу VU. Отдельно измерить холодный кеш.

| Показатель | Предлагаемый стартовый порог |
|---|---|
| Каталог, страница до 20 элементов | p95 ≤ 500 мс при прогретом кеше |
| Федеративная карточка и поиск | p95 ≤ 1000 мс |
| Прикладные mutation без фонового исполнения | p95 ≤ 1000 мс |
| Неожиданные ошибки транспорта или GraphQL | < 1% в базовом профиле |
| Ответ на запуск импорта | p95 ≤ 1000 мс; работа выполняется асинхронно |
| Прогресс subscription | p95 ≤ 2 с от сохранения статуса до получения клиентом при здоровом соединении |

HTTP 200 с непредусмотренным `errors` считается ошибкой. Ожидаемые отказы в отдельном тесте лимитов не смешивать со случайными ошибками. Для подсчёта задержки событий синхронизировать часы либо использовать один измеритель.

Стресс-профиль: ступени 20/50/100 VU по 3 минуты, найти насыщение; не обещать одинаковый SLO на всех ступенях. Прекратить при устойчивых ошибках >10%, исчерпании ресурсов или риске для среды. После снятия нагрузки проверить восстановление и очередь. Отдельно проверить, что массовый импорт не вытесняет интерактивные запросы; ограничить workers/пулы при необходимости.

Порог уточнять до приёмочного прогона по целевой среде и требованиям, с обоснованием в decision record. Не менять его после провала только для зелёного отчёта.

## CI и отчётность

- На PR: статические проверки, модульные тесты, composition, проверка клиентских операций, интеграционные сценарии затронутых областей и короткий E2E.
- Перед выпуском: полный E2E, миграции с чистой и предыдущей схемы, нагрузка, критические fault tests, восстановление бэкапа.
- Live-source smoke: отдельный ручной/контролируемый запуск, без зависимости обычного CI от доступности внешних API.
- Для каждой проверки фиксировать: ID требования, commit, окружение, команду, ожидаемое, фактическое, статус, путь к артефакту и известные ограничения.
- Успешный smoke на 100 пакетах не закрывает R2; синтетический набор закрывает функциональные/нагрузочные сценарии, но не доказательство живого сбора.
