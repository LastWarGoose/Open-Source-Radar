## Продукт

Массовый импорт этапа 5 запускается по [протоколу](docs/decisions/0006-bulk-import.md).
Сохранённый манифест и прогресс находятся в `docs/evidence/stage5/`.

Сайт для поиска, сравнения и отслеживания Python-библиотек. Объединяет сведения о пакетах из PyPI, связанных репозиториях из GitHub и известных уязвимостях из OSV. Помогает оценивать совместимость, зависимости, состояние проекта и известные проблемы конкретных версий.

Первая версия: каталог, страница пакета, сравнение до четырёх пакетов, личные подборки, отслеживание обновлений внутри сайта и административная панель импорта. Интерфейс по умолчанию на русском; исходные названия и описания сохраняются на языке источника. Перевод описаний не входит в первую версию.

Цель наполнения: не менее **10 000 уникальных нормализованных имён пакетов** в локальной базе, а также реальный автоматизированный сбор из всех трёх источников. Версии, зависимости и повторные загрузки не увеличивают счётчик уникальных пакетов. Не для каждого пакета существует GitHub-ссылка или запись OSV; полноту обогащения показываем отдельно.

## Согласованная технологическая основа

- Сайт: TypeScript, React, Next.js App Router, Tailwind CSS, shadcn/ui.
- GraphQL-клиент: Apollo Client и GraphQL Code Generator.
- Backend: Python, FastAPI, Uvicorn, Strawberry GraphQL, DataLoader.
- Federation: Hive Gateway; четыре подграфа по предметным областям.
- Данные: PostgreSQL, SQLAlchemy, psycopg, Alembic; поиск PostgreSQL Full Text Search и pg_trgm.
- Фоновые задачи: Celery, Celery Beat, **RabbitMQ как брокер**.
- Redis: кеш; отдельное назначение/экземпляр для временных результатов задач, если они понадобятся.
- Внешние запросы: HTTPX, Pydantic, Tenacity.
- Наблюдаемость: OpenTelemetry, Prometheus, Grafana, Tempo, Loki.
- Проверки: pytest, Vitest, React Testing Library, Playwright, k6; Ruff, mypy, ESLint, TypeScript.
- Инструменты: uv, pnpm, Docker Compose, GitHub Actions.

Kafka не входит в начальный стек. Вернуться к ней при появлении требований к хранению и повторному чтению потока событий несколькими независимыми потребителями. Количество строк в каталоге само по себе не является основанием для Kafka.

## Что уточнить до соответствующего этапа

| Решение | Рабочее допущение | Когда требуется решение |
|---|---|---|
| Дизайн | [Santal Architecture](https://www.awwwards.com/sites/santal) | Крупная надпись RADAR, светлый первый экран с тонкой сеткой, тёмный каталог и прямоугольные элементы управления |
| Авторизация | Анонимное чтение; HttpOnly-сессия для личных данных; роли user/admin | Реализовано в этапе 6 |
| Вход и восстановление доступа | Локальные аккаунты, пароль и одноразовый код восстановления — выбор пользователя | Реализовано в этапе 6 |
| Размещение и ресурсы | Локальная разработка в Linux-контейнерах, целевой сервер не выбран | До замеров и развёртывания |
| Уведомления | Только внутри сайта, при изменении версии во время импорта | Уведомления реализованы в этапе 6, периодический обход наблюдений — в этапе 7 |
| Политика наполнения | Воспроизводимая выборка пакетов и раскрытая полнота данных | До массового импорта |
| GitHub-доступ | Секрет для API передаётся сборщику через окружение/хранилище секретов | До живого сбора GitHub |

При наведении подсвечивается колонка сетки или строка каталога. Поиск обновляет результаты без перезагрузки страницы. Если в системе включено уменьшение движения, переходы и прокрутка происходят сразу.

Ссылка на сравнение сохраняет выбранные пакеты и режим таблицы. Флажок скрывает строки с одинаковыми значениями во всех колонках. Разное время загрузки само по себе не считается различием.

В карточке и сравнении рядом с результатом указаны версия и дата. Когда запрошенного релиза нет в сохранённых данных PyPI или для него нет успешной проверки OSV, сайт отдельно указывает версию, по которой есть сведения. При выборе ближайшей версии используется порядок PEP 440. Приоритет у той же серии, затем у предыдущего релиза и затем у следующего. Пометка «Исправлено в» показывает версию из диапазона OSV для конкретной находки. Результаты первой загрузки до появления этой функции получают номера исправлений при следующем фоновом обновлении. [Формат диапазонов OSV](https://ossf.github.io/osv-schema/#affectedrangesevents-fields).

В карточке пакета и сравнении у ссылки на репозиторий показывается описание, полученное при фоновом обновлении GitHub. Если описания ещё нет, карточка показывает сводку о пакете с пометкой PyPI, когда она доступна.

Технические страницы health/readiness и метрик могут использовать HTTP вне GraphQL. Все прикладные данные между сайтом и backend передаются через GraphQL. Внешние API не обязаны быть GraphQL.

## Локальный запуск

Нужен Docker Desktop с Linux-контейнерами, Docker Compose и Python 3.12 для
одноразового создания `.env`. Из корня проекта:

```sh
python scripts/bootstrap.py
docker compose up --build -d --wait
```

`bootstrap.py` использует только стандартную библиотеку: создаёт локальные случайные
пароли и временный административный токен, не печатает их и не перезаписывает
существующий `.env`. Можно использовать `uv run python scripts/bootstrap.py`.
Не заменяйте `.env` при существующих volumes: первоначальные пароли уже сохранены
в PostgreSQL и RabbitMQ. `.env.example` содержит только фиктивные значения.

Миграции четырёх сервисов выполняются отдельным контейнером `migrate` перед API
и workers. Успешно завершённый контейнер с кодом 0 — ожидаемое состояние.
При повторном запуске миграции безопасно проверяют текущую ревизию.

Сайт: http://localhost:3000. GraphQL: http://localhost:4000/graphql.
Подграфы, PostgreSQL, RabbitMQ и Redis доступны только во внутренней сети Compose.
Web подключён к отдельной сети со шлюзом. Порты сайта и шлюза привязаны к
loopback; этот демонстрационный запуск не предназначен для внешней публикации.

Главная страница показывает постоянный каталог PyPI. После чистого запуска он пуст;
синтетический seed этапа 2 на публичном сайте скрыт. На текущей машине доступны
FastAPI и requests из живого импорта этапа 3. Карточки: `/packages/fastapi`,
`/packages/requests`; сравнение: `/compare?packages=fastapi,requests`.
Версии и данные ограничены тем, что уже загружено, а даты показаны в UTC.
`SITE_URL` задаёт публичный origin для canonical; по умолчанию localhost и `noindex`.

Демонстрация этапа 0 перенесена на `/demo`. На ней два тестовых пакета.
В раскрывающемся блоке «Обновления» кнопка «Обновить» увеличивает
ревизию fastapi через mutation; подписка возвращает событие с репозиторием из
другого подграфа. Можно приостановить подписку, изменить данные и возобновить её.
При восстановлении соединения клиент повторно читает актуальное состояние.
Значения stars условные. Данные в памяти Catalog сбрасываются при перезапуске.

```sh
docker compose ps
docker compose logs --tail 50 gateway web
docker compose down
```

Остановка сохраняет именованные volumes PostgreSQL, RabbitMQ и Redis и не затрагивает
другие Compose-проекты. Не добавляйте `-v`, если данные нужно сохранить.
Для небольшого публичного импорта GitHub-токен необязателен; при необходимости задайте `GITHUB_TOKEN` локально в `.env`, он передаётся только GitHub worker. Исходная документация сохранена в `docx/`, общие инструкции —
в корневом `AGENTS.md`, новые решения и результаты — в `docs/`.

## Разработка и проверки

На Windows при блокировке PowerShell-обёрток используйте `pnpm.cmd`/`npm.cmd`.
Node на этой машине дополнительно установлен локально в игнорируемой `.tools/`;
Docker-запуск от этой папки не зависит.

```sh
uv sync --frozen
pnpm install --frozen-lockfile
uv run python -m scripts.export_schema
pnpm compose:schema
```

После изменения схемы пересоберите подграфы и gateway, затем обновите типы:

```sh
docker compose up --build -d --wait catalog repositories security workspace gateway
pnpm codegen
pnpm typecheck
pnpm build
uv run ruff check services scripts
uv run ruff format --check services scripts
uv run ruff check packages/python-common/src

pnpm lint
pnpm format:check
pnpm test:contract
pnpm exec playwright install chromium
docker compose build checks
uv run python -m scripts.verify_stage4
pnpm peers check
```

Браузерные тесты требуют запущенного сайта (`docker compose up --build -d --wait`).
`verify_stage4` создаёт временные UI-fixtures, проверяет сортировку и сверку проекции,
запускает Playwright и реальные отключения трёх подграфов, затем удаляет fixtures и
восстанавливает сервисы. Внешние API не используются. `pnpm test:e2e` запускает
только браузерную часть и требует предварительно созданных fixtures. Контрактные
и браузерные проверки запускаются последовательно. SDL и клиентские типы сохранены;
после создания `.env` Docker-запуск не требует локальных зависимостей Python/Node.

## Проверка инфраструктуры и заданий

```sh
docker compose build checks
docker compose run --rm checks
uv run python scripts/verify_infrastructure.py
uv run python scripts/check_secrets.py --logs
```

Первый тест проверяет миграции, изоляцию четырёх ролей, отказ без административного
токена, идемпотентность конкурентных запросов, outbox, завершение worker и Redis.
Полный `verify_infrastructure.py` дополнительно проверяет обработку двух повторных
доставок по логам, correlation ID, недоступность брокера, сохранность сообщения
после перезапуска RabbitMQ и данных после пересоздания контейнеров. Он временно
останавливает локальный стек, сохраняет volumes и в конце восстанавливает сервисы.
Каждый прогон оставляет несколько пробных Job для проверки сохранности.

Технические операции `requestProbeJob(requestKey: UUID!)` и `probeJob(id: UUID!)`
доступны через общий GraphQL endpoint с заголовком `x-dev-admin-token` из `.env`.
Скрипт `checks` передаёт его автоматически, без вывода значения. Повтор одного
`requestKey` возвращает тот же Job. Это временная dev-защита, а не аккаунтная система.
Пробная задача не обращается к внешним API; текущий интерфейс её не запускает.
`/health` — liveness, `/ready` дополнительно проверяет доступ к мигрированной БД.

Workflow [.github/workflows/ci.yml](.github/workflows/ci.yml) запускает статические,
контрактные, браузерные и инфраструктурные проверки без живых API PyPI/GitHub/OSV.
Fixtures находятся в `tests/fixtures/`. Общий Python-пакет содержит только
подключения и телеметрию; модели и миграции остаются у каждого сервиса.

Миграции `_0002` добавляют 14 предметных таблиц, не удаляя Job/outbox этапа 1.

```sh
docker compose build checks
docker compose run --rm checks .venv/bin/python -m scripts.seed_stage2

```

Seed содержит 108 пакетов, 114 релизов, зависимости, два общих репозитория, разные
состояния сканирования и две приватные подборки. Все записи имеют синтетическое

требования о 10 000 пакетах. `verify_stage2` включает seed, проверки схемы и БД,
пагинации, прав и SQL-бюджета, затем кратковременно останавливает Security и
восстанавливает его после проверки частичного ответа.

Пример запроса через http://localhost:4000/graphql:

```graphql
query CatalogPage($after: String) {
  packages(first: 20, after: $after, search: "fastapi", sort: NAME_ASC) {
    nodes {
      id
      name
      source
      releases(first: 5) {
        nodes {
          version
          scan { status source findings(first: 5) { nodes { id summary } } }
        }
        pageInfo { hasNextPage endCursor }
      }
      repositories(first: 5) { nodes { status repository { fullName stars } } }
    }
    pageInfo { hasNextPage endCursor }
  }
}
```

Для следующей страницы передайте `endCursor` в `$after`, сохранив поиск, фильтр
и сортировку. Доступны `NAME_ASC`, `UPDATED_DESC`, `STARS_DESC`, `RELEVANCE`, фильтры `license`,
`hasReleases` и `source` (`PYPI`/`SYNTHETIC`). `releases` также принимает `source`.
Лимит каждого списка — 100. Курсоры нельзя переносить между разными родителями,
фильтрами и владельцами. Зависимости — объявленные требования, а не разрешённое дерево.

Workspace предоставляет чтение `myCollections`, `collection`, `myNotifications`.
Тестовые владельцы определены в `services/workspace/access.py`; `x-workspace-token`
проверяется в сервисе, `x-user-id` не даёт прав. Проверочный скрипт сам создаёт
HMAC-credentials из локального dev-секрета и не выводит их. Вход, CRUD подборок и
пользовательские сессии относятся к этапу 6. `importJobs` доступен с dev-admin токеном;
реальное выполнение импорта реализовано в этапе 3.

Совместимость демо сохранена через отдельные `DemoPackage`, `demoPackages`,
`demoPackage`, `advanceDemo` и `packageUpdated`. `packages` и `package` теперь читают
постоянную модель. Клиентские операции демо обновлены и типы пересозданы.

## Импорт из трёх источников

Запуск — GraphQL mutation `requestImport(requestKey: UUID!, targets: [ImportTarget!]!)`
с локальным `x-dev-admin-token`. Один target содержит `name` и необязательную
`version`; максимум 20. Одинаковый requestKey с теми же параметрами возвращает
прежний Job. Для нового обновления используйте новый UUID.

```graphql
mutation Start($key: UUID!) {
  requestImport(requestKey: $key, targets: [
    {name: "fastapi"}, {name: "requests", version: "2.31.0"}
  ]) { id status processed }
}
```

requests 2.31.0 здесь — исторический пример для проверки OSV. Это не рекомендация
к установке. `importJob(id)` / `importJobs` показывают прогресс PyPI; успех PyPI
означает сохранение данных и постановку обогащения, а не завершение GitHub/OSV.
Их задания читаются через `repositoryImportJob` и `securityImportJob`.
`resumeImport(id)` продолжает failed-части PyPI с сохранённого checkpoint.
Публичные `pypiFreshness`, `githubFreshness` и `Release.scan` показывают результат
проверки, дату последнего успеха и ошибку. При отказе источника предыдущие данные сохраняются.

```sh
docker compose build checks
uv run python -m scripts.verify_stage3
docker compose run --rm checks .venv/bin/python -m scripts.source_report
# Отдельная живая проверка: два прогона по двум пакетам, реальные внешние запросы.
uv run python -m scripts.live_stage3 --output docs/evidence/stage3-live.json
```

`verify_stage3` временно останавливает только Beat и три import-worker и восстанавливает
их после проверки; внешние API заменены синтетическими ответами. Обычный CI не
запускает `live_stage3`. Beat восстанавливает доставку существующих заданий;
